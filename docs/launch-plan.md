# AFTER YOU：72 小时发布与增长计划

计划日期：2026-10-27。H0 指本任务开始时间，开发与传播都计入用户要求的三天窗口；不得以延迟部署重新起算。本文是执行计划，不代表已发布、已取得流量或已完成外部宣传。

目标：让真实玩家愿意再玩一局、把同一挑战传给朋友，让开发者能读懂、运行和改造源码。10,000 GitHub stars 是结果目标，记入真实观测；没有达成时保留实际数值。传播与开发分别验证，不用浏览量代替留存，也不用游戏访问量代替仓库关注。

## 发布前验收

对外玩法以 `design-spec.md` 为准：60 秒收集光点，留下重复过去动作的回声，再冲刺穿过回声得分。早期研究中的合作解谜方案已不用于发布文案。

| 可公开表述 | 发布证据 | 未通过时的处理 |
| --- | --- | --- |
| 可在浏览器直接试玩 | 从无痕窗口打开正式 URL，完成一局并重开 | 暂停公开引流，修复部署 |
| 键盘、鼠标与触摸操作 | 桌面键盘/指针及真实触摸设备完成游戏；模拟触摸仅作为补充 | 文案仅列实测设备 |
| 每日相同挑战 | 相同规则版本、种子和输入得到相同模拟结果；跨日期边界验证 | 暂用普通随机模式 |
| 可分享挑战 | 第二个干净浏览器打开生成链接，关卡参数一致并可开玩 | 隐藏无效分享入口 |
| 确定性回放 | 自动测试证明相同输入日志重放结果一致；渲染快慢不改变模拟；坏数据被拒绝 | 不使用“确定性”宣传措辞 |
| 零运行时依赖 | 检查发布版本依赖清单与网络请求；本地服务仅使用 Node 标准库 | 改成实际依赖描述 |
| 源码开放、规则可改 | 公共仓库含真实许可证、运行命令、规则入口和测试，干净检出可复现 | 不提前宣称开源已发布 |

运行当前仓库定义的 `npm test` 与 `npm run check`，将结果附到发布记录。检查真实截图、移动端可视范围、静音、暂停、重开与无障碍入口。演示只录制发布版本的真实游戏；AI 美术、开发辅助和可选模型能力如被问及应按实际情况说明。

`{{PLAY_URL}}`、`{{REPO_URL}}`、`{{REPLAY_DOC_URL}}` 是文案模板变量，发出前替换为已验证地址。游戏密钥不得进入客户端、仓库、录像或文档；没有接入模型功能时不宣传“AI 驱动玩法”。

## 72 小时节奏

| 时间 | 工作 | 本阶段可检查产物 |
| --- | --- | --- |
| H0–H6 | 固定发布版本；录制一次真实15秒演示；整理双语说明和三张实机截图；邀请愿意试玩的人观察首局 | 正式链接、版本号、验收结果、首局反馈原话 |
| H6–H12 | 达到20个真实开玩样本后检查是否理解“冲刺打碎回声”；修复一个最普遍的理解或操作问题 | 首关/首局完成计数、问题频次、修复前后录屏；样本不足就注明不足 |
| H12–H24 | 在自有渠道发布一个玩家向入口；准备 itch.io HTML5 页面；按对应社区现行规则选择一个欢迎作品展示的社区 | 每个渠道一个可玩链接、来源标签和原帖地址；当天回应实际反馈 |
| H24–H36 | 面向开发者发布可复现的回放机制说明，展示一次修改规则及其测试；仓库首页放试玩与贡献入口 | 真实技术说明、运行步骤、规则示例、3个有验收条件的贡献任务 |
| H36–H48 | 按首局和分享数据选择一个瓶颈；若产品有足够实质与可讨论的技术细节，再考虑 Show HN | 一个修复版本或一个明确保留的设计；记录改动与对应指标 |
| H48–H60 | 发布真实更新：修复了什么、玩家仍在哪里卡住；将支持者自愿提供的回放或关卡展示出来 | 作者许可与署名、有效挑战链接；没有玩家作品则展示自己的实例 |
| H60–H72 | 核对真实 stars、仓库流量与游戏数据；按设备/来源分开看；决定下一轮只改一个问题 | 72小时实测表、已知限制、下一轮假设；没有数据的格子标“未采集” |

这不是自动投放安排。当前任务只准备材料，不发帖、私信、邮件或邀请。后续获得相应发布授权并具备账号后才执行外部动作。

## 玩家传播与开发者贡献

玩家入口只要求“玩一分钟”。结束页先给再来一局和挑战链接；分享卡包含真实成绩、规则版本和种子，不显示答案式回放、不伪造全球排名。接收者可直接开始同题，玩完后再比较分数。分享是自选行为，不以分享、拉人或 star 解锁内容。

开发者入口展示三项具体价值：

1. **确定性回放**：输入日志如何变成固定步进模拟、如何核对最终状态、如何兼容规则版本。配可执行测试及一份小回放样本，不只写口号。
2. **零依赖与可改规则**：指明实际配置入口，示范改一个冲刺/回声参数后如何运行与验证；区分浏览器运行时、开发工具及可选服务。
3. **有边界的贡献**：关卡/规则挑战需提供种子与可完成证据；本地化需核对窄屏；回放缺陷需提供规则版本、日志和期望行为。只有这些入口实际存在时才公开邀请。

README 的 star 请求保持可选：“如果这个游戏或回放实现对你有用，可以在 GitHub 收藏。”它不进入核心游玩流程。不要在其他仓库的 issues/PR 中贴推广，不购买或交换 stars，不组织投票，不使用虚构徽章、用户评价或下载数。

## 测量与迭代条件

以下数值是这个项目的内部行动阈值，不是行业基准或增长预测。分母、时间窗和版本必须一起记录；所有百分比同时列原始计数。低样本只用于找明显问题，不用于宣布“增长验证成功”。

| 指标 | 口径 | 行动条件 |
| --- | --- | --- |
| 首局启动 | 成功进入模拟的唯一会话 / 到达可玩页的唯一会话 | 有至少50次到达但不足25次开玩：先查加载、首屏和操作提示，暂缓增加渠道 |
| 玩法理解 | 能不经提示说明回声与冲刺关系的试玩者 / 被观察试玩者 | 20人中少于14人说清：改首局反馈或提示，然后再观察下一批 |
| 第二局率 | 首局结束后本次会话再次开玩的会话 / 首局结束会话 | 至少50个结束会话但少于15个再玩：优先改难度曲线、即时重开和首轮爽点 |
| 挑战启动 | 打开有效挑战链接后开玩的会话 / 挑战到达会话 | 至少20次挑战到达但少于10次开玩：先修分享落地流程 |
| 分享意图 | 点击挑战分享的会话 / 结束会话 | 记录意图，不将点击当成功发送；100个结束会话仍为0：重做结束页的挑战理由 |
| 技术文档吸引力 | 仓库到达与文档浏览的可得聚合数据 | 游戏持续有人玩而仓库少人看：改善开发者入口与技术说明，不向玩家施压 |
| GitHub stars | GitHub官方显示的实际计数及时间戳 | 记录净变化；与仓库访问量只能作同期描述，不能冒称精确因果转化 |
| 错误 | 无法开始、卡死、无效挑战、回放失配的可复现次数 | 任一核心阻断立即暂停扩散并修复；不等样本满 |

无服务端分析时，浏览器本地计数不能推算全站用户数。可先使用自愿试玩记录和平台提供的聚合流量；新增遥测应保持最少字段、公开说明，不收集原始按键、姓名或指纹。来源标签不含个人信息；排行榜、会话数、留存等功能未上线就写“未采集”。

规模的算术示例：如果每100名有效玩家中有10名访问仓库，其中10%收藏，玩家到star约为1%；新增10,000 stars需要约100万有效玩家。这里的两项比例均是假设，用于说明量级，不用于承诺结果。

72小时后仍无足够真实样本：停止增加传播渠道，先获得可观察试玩。两轮首局修改、每轮至少20次自愿观察后仍不足半数理解核心机制：停止添加内容，重做教学或缩减机制。第二局率提升而分享弱：保留核心玩法，单独迭代挑战理由。产品持续出现阻断错误：暂停传播，不停止修复。达到10,000 stars也不替代可玩性验证。

## 核验来源

- [Show HN Guidelines](https://news.ycombinator.com/showhn.html)：提供可亲自体验的作品，讲清制作思考；快速生成的一次性作品和单纯落地页不符合其定位，也不得请求朋友投票。
- [GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies)：禁止自动刷star、虚假互动和过量推广；项目自身README可使用相关介绍。
- [itch.io 创作者入门](https://itch.io/docs/creators/getting-started)：支持HTML5嵌入、封面、截图和私有预览；公开页面前先完成预览检查。

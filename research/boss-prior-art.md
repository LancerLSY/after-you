# “把自己的轨迹变成朋友的 Boss”独立红队

检索日期：2026-10-27。任务是检验直接同类与手机社交传播假设。本轮只检索开发者页面、官方说明与作者技术文章；没有运行、反编译或复制这些游戏。文档证据说明作者公开提供或描述了什么，不等于本轮实机验收。检索没有覆盖所有作品，不能据“没搜到完全一样”宣称首创。

**判断：继续做一个受限原型有价值，但“动作录制→敌人”和“回放塞进链接→朋友挑战”都已有直接先例。** 将现有回声放大、加血条、改名 Boss，不构成有说服力的玩法差异。机会在于让玩家用几秒动作完成一次有个人特征、可读、可反制的攻击编排，并让朋友愿意用新动作回应。这仍是待测假设，不能推出爆款或万星。

## 五条可验证差异与否决条件

下面是设计假设及内部原型门槛，均未达成；不是行业指标，也不是可专利性结论。

| 候选差异 | 应该做出的可见行为 | 验证方式 | 否决或改向条件 |
| --- | --- | --- | --- |
| 1. 动作是攻击编排，朋友面对的是可反制的招式 | 一段8–12秒动作形成有预警、攻击窗口和恢复窗口的短Boss战；创作者能预览它怎样威胁对手。不能仅把同一路径画得更大。 | 准备直线、绕圈、停顿冲刺三种输入；固定其他参数，检查输出确实形成不同攻击节奏；10名盲测者看输入与战斗配对。 | 若输出主要由随机模板决定、10人中不足7人能把自己的输入与Boss匹配，撤回“你的动作就是Boss”的主张，修映射而非加剧情。 |
| 2. 能读懂朋友的习惯，并通过学习反制 | 保留能识别的路线特征；第一次输后玩家知道下一次躲哪里，成功并非只靠随机安全区。 | 同一Boss三次尝试；记录受击原因、是否改变路线及改善，另给一个伤害量相同的模板Boss作对照。 | 20人中多数无法解释一次受击，或第三次表现没有可观察改善：先改预警/命中判定；不能用“更难”替代深度。 |
| 3. 创作比普通关卡编辑轻，且不奖励无解垃圾关 | 手机上单手动作即可生成；强度受预算限制；创作者必须在发送前打通自己的Boss，系统限制不可避免伤害。 | 10名首次玩家独立生成并完成自测；另测静止、边缘绕圈、快速抖动、长按冲刺、极端采样输入。 | 少于8人能在60秒内完成第一份可玩挑战，或可生成稳定无解/平凡挂机Boss：先简化制作与约束。自测通关只是可解性证据，不保证新手公平。 |
| 4. 回应能改变挑战本身 | 朋友击败后用一段自己的动作作“回招”，保留前一段可识别特征，产生新的短战斗；明确代际和规则版本。 | 与“打完只发自己的无关ghost”比较，观察是否自发制作回招，原作者是否打开并应战。 | 只有按钮点击，没有真实接收和开玩，或回招仅仅更换昵称/分数：不宣称社交创作。先做一对一往返，不堆多人谱系。 |
| 5. 从手机聊天到动手只需一个轻入口 | 接收页先展示“朋友留下的Boss”及一眼可懂的动态预览，直接开打；无强制注册和下载；损坏/旧版本链接有明确结果。 | 真机使用常用聊天App传链接，覆盖 iOS Safari、Android Chrome 以及实际内置浏览器；检查完整性、横竖屏、首触控、音频与暂停。 | 20次真实传送有超过1次无法进入，或收件人需复制代码/手工换浏览器才可玩：暂停传播试验。无后端和短链接本身不是玩法创新。 |

若三天只能实现一项：先做“8秒动作→预览→自测→朋友30秒应战”的单次往返，保留现有回声模式作基线。回招是下一步实验；没有完整验收就不写进对外文案。

## 手机社交传播实验：测实际接收与再传播

**核心问题**：在同样的美术、难度、奖励和页面速度下，玩家是否比普通同种子比分挑战更愿意把自己编排的Boss交给朋友，而且朋友确实开玩、回应？技术测试与真人体验实验必须分开。机器人、模型试玩和浏览器脚本只能验证功能，不能充当用户需求或社交传播证据。

### 阶段一：6对好友，验证流程，不估计增长

招募双方都自愿的6对熟人，各用自己的手机、惯用聊天工具、实际移动网络；至少覆盖 iOS 与 Android。测试者制作挑战、亲自选择发送、朋友从聊天打开。观察员只记录，不接管操作。首次任务的分享是被实验要求的，不能计为自发传播。记录哪一环失败及完成时间，修复后重新验收同一故障；不用新用户掩盖旧故障。

### 阶段二：24对好友，做有对照的方向性试验

按好友对随机分两组，每组12对；设备类型分层，避免同一朋友圈跨组相互影响。A组是现有同种子比分挑战，B组是动作编排Boss。相同首屏、时长、品牌、音量、分享入口位置和奖励；不奖励分享，不提示“请发给更多人”。两组都只安排第一次好友传递，之后24小时不催促。

这是可用性与方向性pilot，样本不足以证明微小增长差异。先冻结版本、指标和观察窗，报告每对的结果；不要在中途挑有利分组。若需要隔离“是朋友制作”本身的作用，后续再对比B组与同样难度的系统模板Boss，不能从A/B组合实验直接断言身份感导致增长。

### 必须记录的链路

| 阶段 | 事件/分母 | 能说明什么 |
| --- | --- | --- |
| 做出Boss | `boss_validated / creator_started` | 制作和自测有没有阻碍；保留时长与失败原因 |
| 想分享 | `share_intent / boss_validated` | 只是意图；打开分享面板不等于消息已发送 |
| 真实送达 | 自愿测试中的双方确认发送/收到；公开自然流量不猜送达数 | Web Share Promise成功也不等于朋友收到或读到 |
| 接收者到达 | 干净设备加载有效挑战的唯一会话 / 已确认收到人数 | 链接与预览是否让人愿意点开；无人确认时分母标未知 |
| 接收者开玩 | `recipient_start / recipient_landing` | 页面、解释、触控是否顺畅 |
| 第一次完整尝试 | `recipient_attempt_end / recipient_start` | 游戏是否能顺利体验；输赢都算完整尝试 |
| 主动再试 | 24小时内至少第二次尝试的接收者 / 完整尝试接收者 | 对局重玩意愿；排除脚本及同次刷新 |
| 回招真正被玩 | 原作者实际开始朋友回招 / 已开玩第一份挑战的好友对 | 一对一社交闭环；创建链接或点击“分享”不算 |
| 第二跳新增玩家 | 未参与初始测试、第一次接触游戏的自愿接收者实际开玩数 / 初始开玩接收者数 | 候选自然扩散信号；研究人员要求的发送全部排除 |

使用随机实验ID、挑战ID、父挑战ID、规则版本与阶段事件；不读取通讯录/聊天内容，不用昵称判断唯一玩家，不做跨站指纹。参与者自愿确认谁是新接收者；身份无法确认时报告会话数与重复风险。后台没有遥测时，用双方自愿记录的表格，不把 `localStorage` 当全站数据。URL可被编辑，因此公开链接成绩只适合友谊挑战，不能伪装成可信全球榜单。

### 预先写下的行动条件

1. **技术停止线**：任一可复现回放失配、无解Boss或隐私泄露立即暂停该版本传播，先修复；20次真机链接传递至少19次成功进入才开展对照试验。
2. **制作停止线**：10位首次创作者中少于8位独立完成制作、自测与可分享状态，暂停增加Boss花样，改制作流程。
3. **传播假设否决线**：B组12对中少于4对完成“朋友实际开玩回招”，不把该原型当作已形成传播循环；优先检查制作负担、收件人理解和是否有回应理由。A/B差异只报原始计数，不在小样本下宣布显著胜出。
4. **继续迭代条件**：B组至少4对完成往返，且高于A组对应二次挑战往返，技术与完成率未退化：进入更大样本的同设计复测，不能立即宣布爆款。样本不齐则延长观察或明确证据不足，不把缺失当失败/成功。
5. **扩散判断**：真实第二跳为0时，只有熟人往返可用性证据；第二跳存在时仍记录人数与选择偏差。只有多个独立自然群体持续出现新增玩家和次日回访，才值得扩张渠道。stars单独从GitHub读取，任何对局指标都不能换算成已获得stars。

没有找到完全相同的完整组合，不构成优势；与现有方案相比，真实玩家更容易创作、更愿意应战并主动回应，才是继续投入的依据。
